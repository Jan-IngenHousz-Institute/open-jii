# Translations

`packages/i18n`, and how the web app and the mobile app use it. It wraps i18next and keeps the
translation bundles in the package rather than fetching them.

The rule that every user-facing string goes through this package is in [prose.md](prose.md) with the
rest of the copy rules. This document is about the mechanics.

## Read first

- `packages/i18n/src/config.ts`, which decides which locales exist and which are switched on.
- `apps/web/components/organizations/organization-and-sharing-strings.test.ts`, whose docblock is an
  honest account of how little is actually guarded.

## Shape

```text
src/config.ts     the locale list, isKnownLocale, the Next routing config
src/server.ts     initTranslations, for server components
src/client.ts     useTranslation, for client components
src/index.ts      a 62-line re-export surface
locales/en-US/    13 namespace files
locales/de-DE/    the same 13
locales/nl-NL/    the same 13, maintained but not enabled
```

The namespaces are `common`, `navigation`, `experiments`, `experimentData`,
`experimentDashboards`, `experimentVisualizations`, `iot`, `macro`, `account`, `dashboard`,
`newsletter`, `publicMetrics` and `workbook`.

## Rules

1. Add a key to `en-US` and `de-DE` in the same change that uses it, and to `nl-NL` as well. Only
   the first two are enabled in `config.ts`, but all three directories are kept in step and the
   coverage test checks all three. [review]
2. Keys are dotted and namespaced, and they live in the namespace that owns the surface. Pick the
   existing namespace before adding a new one; thirteen is already a lot. [review]
3. Interpolate with `{{name}}`. Never assemble a sentence by concatenating translated fragments,
   because word order differs between languages and the result cannot be translated properly.
   [review]
4. No fallback string in a `t()` call. A missing key is a bug to fix in the locale file, and a
   fallback hides it in the one place someone would notice. [review]
5. Client components import `useTranslation` from `@repo/i18n/client`, and server components import
   `initTranslations` from `@repo/i18n/server`. Do not reach for the package root. [review]
6. A key built at runtime, such as ``t(`organizations.roles.${role}`)``, is invisible to the
   coverage test. When you write one, add the full list of possible keys to the enumerated list in
   the guard test so something still checks them. [review]
7. Strings that a user reads in the mobile app go through mobile's own locale files under
   `src/shared/i18n`, not through this package's. [review]

## Patterns

**Adding a surface.** Put its keys under the namespace that already covers the area, add them to all
three locale directories, and use `useTranslation()` in the component. There is an example in almost
any component; 531 files in the web app already call it.

**Checking your work.** The only automated coverage guard reads the `organizations.*` and
`sharing.*` keys out of the source with a regex and asserts each one exists in all three locales.
Every other prefix, including `experiments.*` and `workbooks.*`, is unguarded, so for those the
check is you opening the other two files.

**Why tests assert on keys.** `apps/web/test/setup.ts` mocks this package so `t(key)` returns the
key itself. That means a web test asserting visible text is asserting the key string, not the
English copy, which is deliberate: it keeps tests from breaking when wording changes.

## Tests

The package itself has none. What exists is the guard test in the web app described above, plus a
matching pair in mobile for its role and type labels. That is the whole of it.

## Known debt

`src/index.ts` is a 62-line re-export surface covering `./config`, `./server`, `./client`, about
fifteen i18next runtime functions, the Next routing helpers and a dozen types. It contradicts rule 8
of [code.md](code.md), and it is unnecessary now that `@repo/i18n/client` and `@repo/i18n/server`
exist as subpaths. Splitting consumers onto those two and deleting the rest is mechanical. Needs a
ticket.

`createTranslationKey<T extends string>(key: T): T` returns its argument unchanged. It looks like it
validates a key and it does not, which is worse than not having it. Delete it or give it a real
implementation. Needs a ticket.

Locale coverage is guarded for two prefixes out of thirteen namespaces. A key added to
`experiments.*` in English only ships, renders the raw key in German, and nothing fails. Extending
the guard to every namespace is the obvious fix and would probably surface existing gaps. Needs a
ticket.

`nl-NL` is fully maintained and commented out of the locale list, so the work of keeping it current
buys nothing today. Either enable it or say in `config.ts` when it is expected to ship. No ticket.

31 em dashes are shipping in the locale files, 12 in `en-US`, 9 in `de-DE` and 10 in `nl-NL`,
against rule 2 of [prose.md](prose.md). Needs a ticket.

`isKnownLocale` in `config.ts` uses a type assertion to narrow the argument for `includes`, which
[code.md](code.md) rule 1 forbids. `locales.some((known) => known === locale)` does the same job
without it. No ticket.

## Decisions

- 2026-09-21. All three locale directories stay in step even though `nl-NL` is switched off, because
  the coverage test already checks three and letting one rot makes enabling it later a project
  rather than a config change.
- 2026-09-21. Tests assert on key strings rather than English copy, because the package is mocked in
  the web test setup. Changing that would make every wording change a test change.
