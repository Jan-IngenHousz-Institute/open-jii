# ADR: First-party apps reuse the openJII session

**Date:** 2026-11-12  
**Status:** Accepted

## Context

openJII Lab, JII's instrument register, needs openJII sign-in. It is served at
`lab.openjii.org` from its own AWS account, not the openJII platform's.

openJII sets its session cookie on `.openjii.org` (`.dev.openjii.org` on dev). So
whenever a signed-in person opens openJII Lab, their browser already sends openJII Lab
their full openJII session, whichever sign-in protocol openJII Lab uses. An OIDC
provider would not change that. Only a domain outside `openjii.org` would. The
decision is therefore about who sits inside openJII's trust boundary, not about
which protocol to use.

## Decision

openJII Lab reuses the openJII session, and openJII runs no OIDC provider for it.
openJII Lab's server checks the session cookie with openJII's session and
organization membership endpoints, then creates its own application session.
After sign-in, openJII sends people back to openJII Lab only through an allowlist of
return addresses. openJII Lab does not join Better Auth's trusted browser origins.

## Consequences

- Every application under `openjii.org` sees openJII sessions, so each one has to
  meet openJII's bar: the token is never stored or logged, changes are reviewed,
  and its AWS account runs under the same guardrails as openJII's.
- Return addresses are approved by origin, so any path on openJII Lab passes.
  openJII Lab accepts only same-origin relative paths in its own `redirect`
  parameter, so an approved return cannot chain on to another site.
- Better Auth's cookie names, session fields and membership answers become an
  interface. `packages/auth/src/session-contract.test.ts` pins them against the
  real server configuration, and its failure messages say what openJII Lab relies
  on. A Better Auth upgrade that fails that test needs a coordinated openJII Lab
  release.
- After signing out of openJII, people can stay signed in to openJII Lab until its
  next session check. That can take up to Lab's re-check interval. Lab documents
  the interval and its policy for openJII outages in its own repository.

## Alternatives considered

- **An OIDC provider in openJII.** openJII Lab would receive tokens scoped to it,
  but while it stays under `openjii.org` the browser still sends it the session
  cookie. The provider would remove no exposure and add client registration and
  key rotation to run. It becomes worth it when an application outside JII needs
  openJII sign-in.
- **Serving openJII Lab from a domain outside `openjii.org`.** This takes openJII Lab
  out of openJII's trust boundary, but it then needs a provider such as OIDC to
  sign in at all. Not now: openJII Lab is a JII application that can meet openJII's
  bar, and sharing the session lets it ship without a provider.
