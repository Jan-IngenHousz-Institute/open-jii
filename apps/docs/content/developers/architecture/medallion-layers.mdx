The current data platform keeps all research data in one central Unity Catalog schema, `centrum`. This replaces the per-experiment schema model described in the project's 2025 historical ADRs. Two other pipelines write alongside the main one. Macro execution runs in its own pipeline and publishes `experiment_macro_data` and `enriched_experiment_macro_data` into `centrum`, because a macro is a synchronous HTTP call from a Spark task and sharing the ingest pipeline's compute let those calls hold the slots the stream reader needed. A small sibling schema, `metrics`, holds platform activity rollups produced by a separate serverless DLT pipeline reading the centrum tables. Its public-facing tables are aggregate-only; two backend-only tables (`daily_activity_by_experiment`, `experiment_contributors_window`) carry experiment- and contributor-grain rows that the backend aggregates per organization or user and never exposes unaggregated. Experiment isolation is now expressed through experiment identifiers, experiment-facing tables, access checks, and filtered queries rather than a separate Databricks schema for every experiment.

## Layers

| Layer          | Current tables                                                                                                                                                                                                                                                                                                                          | Responsibility                                                                                                                        |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Bronze         | `raw_data`, `raw_imported_data`, `raw_uploaded_data`, `raw_large_data`                                                                                                                                                                                                                                                                  | Preserve source events and source-specific metadata with minimal transformation.                                                      |
| Silver         | `clean_data`                                                                                                                                                                                                                                                                                                                            | Parse and normalize records, decompress samples, validate timestamps, unify MQTT/import/upload sources, and retain provenance fields. |
| Gold           | `experiment_raw_data`, `experiment_device_data`, `experiment_devices`, `experiment_macro_data`, `experiment_uploaded_data`, `experiment_contributors`, `experiment_status`, `experiment_table_metadata`, and the incremental sources beneath them: `bridge_experiment_device`, `bridge_experiment_contributor`, `agg_experiment_device` | Produce experiment-oriented facts, device and contributor summaries, macro output, upload data, status, and query metadata.           |
| Enriched views | `enriched_experiment_raw_data`, `enriched_experiment_macro_data`, `enriched_experiment_uploaded_data`                                                                                                                                                                                                                                   | Join display and user context for application-facing reads without duplicating it into every raw record.                              |

The exact deployed names are configured through `apps/data/src/lib/openjii/openjii/centrum/runtime.py`; the pipeline definitions live under `apps/data/src/pipelines/centrum/`.

## Bronze: preserve provenance

`raw_data` reads the Kinesis stream and retains broker/stream metadata such as the authenticated MQTT client ID, sequence number, shard, arrival time, and ingestion time. The parsed event remains close to what arrived. Imported transfer files and web-uploaded datasets use separate Bronze tables because their provenance and schemas differ.

## Silver: normalize once

`clean_data` turns source records into a common representation. It decompresses `sample` when `_sample_encoding` is `gzip+base64`, validates timestamps, normalizes device and user fields, parses macros/questions/annotations, and unions supported non-MQTT sources. Invalid timestamps are dropped by a DLT expectation; other expectations retain observability without silently inventing values.

## Gold: serve experiment tasks

Gold tables answer application questions without repeatedly unpacking raw JSON. They separate raw measurement rows, device summaries, macro results, uploaded data, contributors, and status. `experiment_table_metadata` caches table schema and row-count information used by pagination and table discovery.

The device and contributor summaries are built in two steps. `bridge_experiment_device` and `bridge_experiment_contributor` hold the distinct pairs that have produced data, and `agg_experiment_device` holds the per-device counts. `experiment_devices`, `experiment_contributors` and `experiment_device_data` sit above them and add the registry and profile lookups. The split exists because a materialized view outside a serverless pipeline is always fully recomputed, so anything sitting above an aggregate forces a full scan of silver on every trigger. With the aggregate alone in its own table, the two bridges are streaming tables maintained by AUTO CDC and process only what arrived.

Flexible result shapes use Databricks VARIANT values where the protocol or macro output cannot be represented by one rigid relational schema. Stable identifiers remain separate from display labels so renaming a macro does not change the table identity.

## Macro execution pipeline

`experiment_macro_data` and `enriched_experiment_macro_data` belong to the macro pipeline, which reads `experiment_raw_data` and the contributor, device, annotation and metadata tables from Centrum. Centrum's `experiment_table_metadata` reads the enriched view by its qualified name and skips it until the view exists, so a fresh environment can run Centrum before the macro pipeline has run once.

An environment where Centrum already owns these tables moves them to the macro pipeline instead of rebuilding them. Rebuilding would run every historical macro through the sandbox again. The macro pipeline must not run before the tables are reassigned, because it cannot define a table another pipeline owns.

1. Stop the Centrum pipeline and wait until it has fully stopped. In dev, pause the ingestion scheduler job first.
2. Apply the change that moves both notebooks from Centrum to the macro pipeline. In dev this creates the macro scheduler job, which runs at quarter past and quarter to the hour; pause it before it first fires. If the macro pipeline started when it was created, stop it.
3. Reassign both tables to the macro pipeline:

   ```sql
   ALTER STREAMING TABLE <catalog>.centrum.experiment_macro_data
     SET TBLPROPERTIES ("pipelines.pipelineId" = "<macro pipeline id>");
   ALTER MATERIALIZED VIEW <catalog>.centrum.enriched_experiment_macro_data
     SET TBLPROPERTIES ("pipelines.pipelineId" = "<macro pipeline id>");
   ```

4. Start the macro pipeline, then Centrum, then resume the schedulers.

Check the first macro update in `macro_execution_pipeline_event_log` before moving production. It should process only the rows that arrived since Centrum stopped. If it processes the whole of `experiment_raw_data`, the stream did not keep its progress through the move, and that has to be resolved before production.

## Why the layers matter

- Bronze retains evidence needed for replay and investigation.
- Silver centralizes compatibility and data-quality logic.
- Gold makes common reads predictable and economical.
- Enriched views keep user-facing joins consistent.

The layers are data-quality stages, not public authorization boundaries. Product access is still enforced by the backend and its experiment membership/visibility rules. See [Data ingestion](/developers/architecture/data-ingestion) for how events enter Bronze.
